# Brainstorm: Notebook Lifecycle & Local Archive

**Date:** 2026-09-29
**Status:** Design agreed, open questions resolved
**Next:** `/ce:plan`

---

## The Problem

Pipeline runs have been failing. Root cause, verified against the live account:

- **499 / 500 notebooks** — the account is at the NotebookLM Plus cap. `nlm notebook create` has nowhere to go.
- **No code anywhere deletes a notebook.** Exhaustive grep found zero deletion, zero TTL, zero cap monitoring. `notebooks.json` grows monotonically and entries are never removed.
- The leak is amplified by failure: last daily-feed artifacts on disk are **2026-06-28**, yet notebooks were still being created through **2026-08-16**. The pipeline creates a notebook, fails downstream, and orphans it.
- Burn rate: **163 notebooks in July, 230 in August**. The weekly triage splits a category into ~15-source sub-notebooks, producing 21-part runs.

### Notebook census (live, 2026-09-29)

| Pattern | Generated by | Count |
|---|---|---|
| `Daily Feed — YYYY-MM-DD` | `daily_pipeline.sh:192,320` | 63 |
| `<Group> - Week of YYYY-MM-DD` | `weekly_pipeline.sh:222` | 399 |

Only **75** of the 474 pipeline notebooks appear in `notebooks.json`. Deleting "what the registry knows" would clean less than a sixth of the leak — classification must come from the live list, matched against the exact title patterns the code emits.

## What We're Building

Make the notebook a **disposable render target** instead of a permanent store. Each run: create → add sources → generate every artifact → capture everything to disk + SQLite → verify → delete the notebook. The account footprint stays flat regardless of how many runs happen.

Four pieces:

1. **`data/research.db` (SQLite)** — durable record of runs, notebooks, sources, artifacts, and share state. Stdlib `sqlite3`, no new dependency. JSON files stay as-is so the existing pipeline keeps working; the DB becomes the system of record.
2. **Full capture before delete** — `nlm download all` for every artifact type (report, audio, mindmap, slides, video, infographic, quiz, flashcards, data-table), plus `nlm source content` for the extracted text of every source, notes, and chat history.
3. **Local RAG** — index the captured source text and full report bodies into ChromaDB so `/chat` answers locally with citations, instead of calling `nlm notebook query` against a live notebook.
4. **Backfill** — one-off salvage sweep over the 474 existing pipeline notebooks: download what exists, record it, delete. Recovers ~3 months of never-downloaded podcasts and reports and frees the cap.

---

## Why This Approach

The cap is not a quota to be managed — it is a symptom of treating a rendering service as a database. NotebookLM is good at generating artifacts and bad at being permanent storage: no versioning, no backup, no query API beyond chat, and a hard object limit. Once artifacts are on disk and indexed locally, the notebook has no remaining job.

This also fixes things that are already broken independent of the cap:
- `/chat` today only works for notebooks that still exist; local RAG covers **all** history, not the 75 registered ones.
- `/generate report|podcast` re-downloads from the live notebook at request time (`fetch_and_deliver.sh:153-207`) — slow, auth-dependent, and fails for any notebook that's been touched since. Serving from disk is strictly better.
- Share links emitted to Telegram are never persisted anywhere except on the Playwright path.

---

## Key Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | **Full local RAG**, not a rolling window | A retention window keeps the cap dependency alive and silently loses old history. Indexing captured text makes `/chat` permanently cap-immune and broader than today. |
| 2 | **SQLite** at `data/research.db` | Repo has no relational store; `notebooks.json` is already drifting (75 registered vs 474 live) and has no query story. Stdlib, zero new deps. |
| 3 | **Salvage, then delete** the 474 | Three months of podcasts/reports were generated and never downloaded. Deleting without salvage discards them permanently. |
| 4 | **Strict title-pattern allowlist**, derived from the generating code | The 24 personal notebooks are the hazard. Match only strings the pipeline itself emits — never a generic date regex. Legacy `Research Digest` and corrupted `Daily Feed` titles included by explicit pattern. |
| 5 | **Generate the full studio set** before deleting | The notebook is about to be destroyed; artifacts not generated are gone forever. Affordable only because of decision 6. |
| 6 | **Fix weekly split sizing in this change** | 21 notebooks per category makes generating 9 artifact types each unaffordable. Raising the per-notebook source cap to yield ~4 notebooks is what makes decision 5 viable. The two are coupled, not separate. |
| 7 | **Delete only after verified capture** | Deletion is irreversible with no undo. Gate it on a positive check that expected artifacts exist on disk and are non-empty and DB rows are committed. Any failure leaves the notebook alive for the next run to retry. |

## Deletion Blast Radius

Everything that needs a **live** notebook after the run ends. All of it must be repointed before deletion lands.

| Consumer | Site | Breakage |
|---|---|---|
| `/chat` | `src/pipeline/rag_chat.py:74-91` | **Total.** ChromaDB only routes; every answer comes from `nlm notebook query`. |
| chat-rag skill | `skills/chat-rag/SKILL.md:80` | Same. |
| `/generate report\|podcast\|news` | `scripts/fetch_and_deliver.sh:153-207` | **Total** for research/news — downloads on demand, caches nothing. |
| Deep Dive rerun path | `daily_pipeline.sh:574-577` → `deep_dive_generator.py:115-140` | Breaks on any re-run after deletion. Same-run is safe. |
| Share links already in Telegram | `daily_pipeline.sh:665`, `weekly_pipeline.sh:491-500` | Become dead URLs. Never persisted (and at `weekly_pipeline.sh:496-500` the value is computed then discarded). |
| ChromaDB routing rows | 404 embeddings across 56 `notebook_id`s | Orphaned pointers to deleted notebooks. |

Safe (filesystem-only): `/generate daily`, magazine generation, report enhancement, PDF rendering.

**Ordering constraint:** deletion runs after daily Step 8 / weekly Step 7 (delivery). Steps 6.6 and 6.6b both re-query the notebook.

## Incidental Findings

Found while mapping; not the target of this change, but they touch it.

- **`src/pipeline/fetch_latest.py:22`** — `DATA_DIR` resolves to `src/data`, which does not exist after the `refactor/repo-structure` move. `/generate` therefore always falls through to `nlm notebook list`, making even the registry lookup depend on live notebooks.
- **Non-atomic registry writes** — `daily_pipeline.sh:769-771` and `weekly_pipeline.sh:320,570` use raw `json.dump(open(...))` instead of `src/lib/file_utils.save_json`. Corruption risk on crash.
- **`has_podcast` / `has_report` are hardcoded `True`** at `daily_pipeline.sh:757-760` regardless of whether either succeeded.
- **`source_ids` always written empty** for daily notebooks, so `index_notebook.py:52-54` bails and never indexes daily sources — only the report TL;DR.
- **ChromaDB has 0 `companion_note` rows** despite the documented design, and `research_reports` (declared at `src/rag/embeddings.py:52`) was never created.
- **CLAUDE.md is stale**: says `nlm` 0.3.15, installed is **0.9.6**; documents pre-refactor `lib/` and `scripts/*.py` paths.

## Resolved Questions

- **What happens to `/chat`?** Full local RAG over captured source text and report bodies. No live-notebook dependency.
- **Where do links and generations live?** SQLite at `data/research.db`.
- **The 474 existing notebooks?** Salvage whatever artifacts already exist, record them in the DB, then delete.
- **The 12 legacy/corrupted titles?** Include them via explicit additional patterns (`Research Digest - <date>`, corrupted `Daily Feed` prefix, the untitled 0-source one).
- **How far does "download all resources" go?** Generate and capture the complete studio set — mindmap, slides, video, infographic, quiz, flashcards, data-table — on top of report and audio, plus source text, notes, and chat history.
- **Weekly burn rate?** Fix it in this change; it is a prerequisite for affording the full studio set.
- **Backfill depth?** Download-only for the 474 existing notebooks — capture what was already generated plus source text, then delete. The full studio set applies to new runs going forward, where decision 6 makes it cheap.
- **Large artifacts (video etc.)?** If it gets generated, it gets delivered to Telegram. Locally, keep a compressed copy and discard the oversized raw — mirroring the existing podcast pattern (`-podcast-raw.mp4` → ffmpeg → `-podcast.mp3`, deliver the compressed one). Nothing is lost but fidelity.
- **Dead share links?** Stop emitting `nlm share public`. Telegram already receives the PDF and MP3 directly, and `weekly_pipeline.sh:496-500` computes the link then throws it away.

## Open Questions

1. **Audio download path.** BUG-001 (`httpx` TooManyRedirects) means `nlm download all` likely cannot fetch audio; the CDP/Playwright workaround is probably still required for the audio type specifically. To be verified during planning, not a product decision.
2. **Telegram size ceiling for video.** The Bot API caps uploads well below a typical raw video overview. Assumption to validate in planning: compress video to fit, same as audio; if a compressed artifact still exceeds the ceiling, deliver a note instead of the file and keep the local copy.
